KIO2: find where a Python program failed

KIO2 runs a failing Python program once, records every statement it executes, and works backwards from the error to the lines that caused it. It reports those lines with the values they held at the time of the failure.

How it works

1 Record KIO2 runs the program under the FocusTracer engine. Every executed line, and the variables it read and changed, goes into a trace file (XML).
2 Slice Starting at the line that raised the error, KIO2 follows the recorded values backwards and keeps only the lines that fed into the failure.
3 Report Those lines come back as findings, with the variables in scope at the crash and a link to the trace.

KIO2 does not guess from the source code. Everything it reports comes from a real run. That is why it needs a program it can execute, and why a program that runs without an error is reported as clean.

Input

KIO2 needs two things: the folder of the code and the script that reproduces the failure.

FieldMeaning
repositoryThe project folder. The script runs with this folder as its working directory, and KIO2 looks here for the functions to record.
entry_pointThe script that shows the failure, for example a small reproduction or a failing test.
traceOnly for replay and comparison: a recording made by an earlier KIO2 step.

From KIO1 these arrive as references, for example:

"data": {
  "repository":  { "uri": "file:///workspace/shop" },
  "entry_point": { "uri": "file:///workspace/shop/tests/reproduce.py" }
}

A task text, a test name or an artifact name alone is not enough: KIO2 has to know what to run.

Output

The reply for the bundled example (a shopping cart where no item is in stock, so the average price divides by zero):

{
  "summary": "Located the fault at buggy_order_total.py:15 (average_price).",
  "verdict": "defect",
  "findings": [
    { "line": 15, "dependency": "criterion", "confidence": 0.85,
      "description": "return total / len(prices)" },
    { "line": 19, "dependency": "data", "confidence": 0.425,
      "description": "avg = average_price(items)" },
    { "line": 11, "dependency": "data", "confidence": 0.425,
      "description": "prices = [it[\"price\"] for it in items if it[\"in_stock\"]]" },
    { "line": 12, "dependency": "data", "confidence": 0.425,
      "description": "total = 0" }
  ],
  "crash_state": { "prices": "[]", "total": "0", "items": "[...]" },
  "trace_ref": "kio2://trace/...",
  "trace_url": "/traces/..."
}
FieldHow to read it
verdictdefect: lines were found. clean: the program finished without an error. inconclusive: it failed, but no line could be tied to the failure.
findingsA chain read backwards from the error. The first line is where the error happened. The next ones produced the values it used. It is not a ranking of guesses; deciding where to fix is left to the developer or to KIO7.
dependencycriterion: the failing line. control: a condition that decided the failing line would run. data: a line that produced a value the failing line used.
confidenceA fixed rule, not a probability: 0.85 when the failing line is found, lower otherwise, scaled by the dependency. Below 0.6 the reply asks for human review.
crash_stateVariables at the moment of the error, shown as Python would print them.
trace_ref, trace_urlThe recording. Pass trace_ref to a replay or comparison step. Open trace_url on the KIO2 address to see the XML in a browser.

Capabilities

CapabilityWhat it doesNeeds
bug_localizationRecord the program and report the lines behind the error.repository, entry point
diagnosisThe same analysis written as a root cause, plus the annotated slice a fix step (KIO7) can use.repository, entry point
replayMove through a recording line by line, forwards or backwards, and read the variables at any point. Nothing is re-run.a trace
trace_alignmentCompare two or more recordings of the same program and show where their executed lines differ.two or more traces

KIO2 does not write fixes. A request for fix_recommendation is answered with an error, because fixing is KIO7's step.

Called by KIO1

KIO1, the orchestrator, sends KIO2 steps with the same job protocol it uses for every agent:

  1. KIO1 sends POST /jobs with the step: capability, task and data.
  2. KIO2 answers at once with status: "accepted" and a job_id, then runs the analysis.
  3. KIO1 asks GET /jobs/{job_id} every few seconds. While the job runs the answer stays accepted.
  4. The final answer is success with artifacts (the result and the trace) or failure with a failure_class, for example entry_point_missing.
  5. If a later step depends on this one, KIO1 passes the artifacts on. This is how a replay or comparison step receives the recording.

Endpoints

EndpointPurpose
POST /jobs, GET /jobs/{job_id}The job protocol KIO1 uses.

GET /tasksThe capabilities, supported language (Python) and the job protocol version.

Run it

Install the FocusTracer engine and KIO2, then start the service on port 8102:

pip install -e ../../Trace/focustracer
pip install -e .
cd src
python -m kio2.main

Or with Docker. Put the code to analyse under ./workspace and refer to it as /workspace/...:

docker compose up --build

Settings are read from .env (see .env.example), for example KIO2_TRACE_DIR for where traces are written.

Limits

  • Python programs only.
  • KIO2 runs the code it is given. There is no authentication, so run it only on a trusted network and only on code you trust.
  • Traces contain real values from the run and are not deleted automatically.
  • Only failures that raise an error are localised. A wrong result without an error is reported as clean.
