# Working with the schema

## How a trace gets produced

A trace is never handwritten. It is generated by running a Python program
under FocusTracer's recorder, which instruments the target through standard
CPython tracing hooks and writes the resulting XML.

KIO2 triggers this through `src/kio2/runner.py`, which shells out to
FocusTracer's CLI:

```bash
python -m focustracer run <target_script> \
  --function <name> [--function <name> ...] \
  --detail detailed \
  --schema-version 2.3 \
  --output <trace_path>.xml
```

- `--detail detailed` is required for slicing: it is the mode that makes
  FocusTracer write `<reads>` on line events (see
  [Format reference](format.md)). Lower detail levels omit it.
- `--schema-version 2.3` is what KIO2 requests by default
  (`Kio2Input.schema_version` in `src/kio2/contract.py`); ask for an older
  version only if a downstream consumer specifically needs it, since slicing
  requires 2.3.
- `--function` is repeated once per instrumented function. KIO2 fills this in
  automatically when the caller does not name any (see
  [`docs/TECHNICAL_DOCUMENTATION.md`](../TECHNICAL_DOCUMENTATION.md) §3 for
  target discovery).

You do not need to invoke this directly to use KIO2; `runner.run()` (or the
`/execute` API, or the `localize()` / `replay()` / `compare()` library calls)
does it for you and returns the resulting file path as `trace_path`.

## How to validate a trace file

Since the schema is a standard XSD, any XML toolchain can validate a trace
against it. From the command line, with `xmllint` (part of libxml2):

```bash
xmllint --noout --schema schema/trace_schema_v2.3.xsd my_trace.xml
```

Or from Python, with `lxml`:

```python
from lxml import etree

schema = etree.XMLSchema(etree.parse("schema/trace_schema_v2.3.xsd"))
tree = etree.parse("my_trace.xml")
schema.assertValid(tree)  # raises DocumentInvalid with details on failure
```

This is useful when writing a new producer or consumer of the format, or when
diagnosing whether a trace that fails to replay is malformed rather than
merely unexpected.

## Choosing a schema version

Pass a version explicitly only when you have a reason to target an older
consumer; the default is always the current version. In KIO2's contract:

```python
from kio2.contract import Kio2Input

# default: schema_version="2.3" (required for slicing)
inp = Kio2Input(target_script="app.py", functions=["compute"])

# explicit older version, if some downstream reader still needs it
inp = Kio2Input(target_script="app.py", functions=["compute"], schema_version="2.2")
```

Requesting a version below 2.3 disables slicing: `localizer.py` needs the
`<reads>` element that only 2.3 writes, so `fault_localization` requests will
fail or degrade if given an older trace. `replay` and `trace_alignment` only
need the event hierarchy, so they work against any v2.0+ trace.
